# PayGuard roadmap

The plan PayGuard is built against: one branch at a time, each with tests, a pull request, green CI and a merge. ✅ merged · 🔨 in progress · ⬜ not started.

| #                | Branch                   | What it delivers                                                                                                                                                                                                           | Status |
| ---------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------ |
| **Foundation**   |                          |                                                                                                                                                                                                                            |        |
| 1                | `chore/project-setup`    | npm workspaces, strict TypeScript, ESLint, Prettier; Express with health/readiness checks, pino JSON logs with request IDs, zod-validated config; Docker Compose with a Mongo replica set and Redis; Vitest, supertest, CI | ✅     |
| 2                | `feat/merchants-auth`    | Signup/login; short-lived access tokens and rotating refresh tokens in httpOnly cookies with reuse detection; team roles (owner, developer, analyst); hashed test/live API keys; Redis rate limiting; one error format     | ✅     |
| **Money core**   |                          |                                                                                                                                                                                                                            |        |
| 3                | `feat/ledger`            | Double-entry bookkeeping in whole paise, immutable entries in Mongo transactions, concurrency-safe balances, property-based tests                                                                                          | ✅     |
| 4                | `feat/payment-intents`   | Payment state machine, Stripe-style `Idempotency-Key` handling                                                                                                                                                             | ✅     |
| 5                | `feat/razorpay-checkout` | Razorpay orders, the hosted checkout (`apps/checkout`, React), signature verification on the callback, then capture; a full test-mode payment end to end                                                                   | ✅     |
| 6                | `feat/webhooks-inbound`  | Razorpay webhooks verified with HMAC over the raw body, each event processed once (deduplicated by event id), out-of-order events handled, ledger written in the same transaction as the payment update                    | ✅     |
| 7                | `feat/refunds`           | Full and partial refunds as reversing ledger entries; can't refund more than was paid, even when refunds race                                                                                                              | 🔨     |
| 8                | `feat/webhooks-outbound` | Webhooks to merchants signed with a timestamped HMAC; BullMQ delivery with exponential backoff and jitter; dead-letter queue, replay, delivery logs; SSRF protection on webhook URLs                                       | ⬜     |
| 9                | `feat/reconciliation`    | Nightly job matching Razorpay payments and settlements against the ledger, flagging mismatches; settlements recorded; reports                                                                                              | ⬜     |
| **Fraud and AI** |                          |                                                                                                                                                                                                                            |        |
| 10               | `feat/risk-rules`        | Real-time allow/review/block in under 50 ms: velocity (Redis sliding windows), device and IP, amount anomalies, blocklists; merchant-configurable JSON rules; every decision saved with reasons                            | ⬜     |
| 11               | `feat/ml-risk-model`     | Public fraud dataset plus a synthetic generator; features shared by training and serving; versioned model served in Node, shadow mode, catch-rate tracking. **Decided: pure JS, no Python training script**                | ⬜     |
| 12               | `feat/review-queue`      | React dashboard for flagged payments with reasons; no two analysts on one case; decisions saved as training labels                                                                                                         | ⬜     |
| 13               | `feat/ai-analyst`        | LLM case summaries grounded in rule hits, model score and history; similar past cases via vector search; plain-English payment search through a fixed, validated filter set; PII masked; a small evaluation set            | ⬜     |
| **Production**   |                          |                                                                                                                                                                                                                            |        |
| 14               | `feat/analytics`         | Volume, success-rate and fraud-rate charts from aggregation pipelines; daily totals kept current with change streams                                                                                                       | ⬜     |
| 15               | `feat/observability`     | OpenTelemetry traces from API through queue to worker; Prometheus metrics (p95 latency, webhook lag, queue depth); Grafana dashboards and alerts                                                                           | ⬜     |
| 16               | `perf/load-and-security` | k6 load tests with throughput targets, index tuning with `explain()`; helmet, CSRF protection, OWASP checklist                                                                                                             | ⬜     |
| 17               | `feat/e2e-and-deploy`    | Playwright end-to-end tests paying through Razorpay test mode; multi-stage Docker builds; AWS EC2 + MongoDB Atlas, domain, HTTPS, deploy on every merge                                                                    | ⬜     |
| 18               | `docs/launch`            | Architecture diagram, design-decision notes, demo video, optionally Razorpay live mode                                                                                                                                     | ⬜     |

## Notes

- Branch 4's states are `requires_payment → processing → succeeded / failed / canceled` (Stripe's naming) rather than the plan's `created → authorized → captured`. Refunds (branch 7) add the refunded side.
- Live payments need Razorpay to activate the account (KYC, plus a site with terms, refund, privacy and contact pages); that's part of branch 18.
